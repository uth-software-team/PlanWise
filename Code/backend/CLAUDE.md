# CLAUDE.md — Backend (Code/backend)

General rules (approval workflow, git, security, source of truth) are in the root `CLAUDE.md`. This file adds backend rules.

## Stack
Java 25, Spring Boot 4.1.x, Spring Security, Spring Data JPA, Bean Validation, Flyway (`spring-boot-starter-flyway`; migrations in `src/main/resources/db/migration`, Hibernate `ddl-auto=validate`), Lombok (only if already used). Build: **Gradle 9.8** (wrapper).
DB: PostgreSQL 16, `BIGINT` identity PKs, TIMESTAMPTZ, per-user IANA timezone (`users.timezone`). No Redis for MVP.
Check `build.gradle` before adding dependencies. Never bump versions or swap working libraries.

## Commands (run in `Code/backend/`; verify against build.gradle / README first)
- Build: `./gradlew build`
- Test: `./gradlew test` (single: `./gradlew test --tests "ClassName"`) — H2 only, no Docker; excludes `@Tag("pg")`.
- PostgreSQL tests: `./gradlew pgTest` (Testcontainers `postgres:16`, needs Docker; CI job `pg`).
- Run: `./gradlew bootRun`
- DB: `docker compose up -d` in `Code/backend/` (`compose.yaml`), or `./scripts/setup-dev.sh --docker` from repo root. Never `docker compose down -v` (deletes the DB volume) without approval.
Never run migrations or data-changing commands without approval.

## Configuration & Environment
- `Code/backend/.env` (KEY=VALUE) is loaded automatically via `spring.config.import=optional:file:.env[.properties]` in `application.properties`. Precedence: real OS env vars > `.env` > defaults in `application.properties`.
- No `.env` -> fallback to H2 in-memory (`jdbc:h2:mem:planwise`). Never rely on this silently: when PostgreSQL is expected, confirm it.
- Keys: `SERVER_PORT` (default 8080), `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JPA_DDL_AUTO`, `JWT_SECRET`, `JWT_EXPIRATION_MINUTES`, `CORS_ALLOWED_ORIGINS`.
- Local PostgreSQL: container `planwise-postgres` (PostgreSQL 16), DB `planwise_ai`, user `planwise_user`, port 5432. `compose.yaml` (project `planwise`, volume `planwise_postgres_data`, bound to 127.0.0.1) reads `DB_USERNAME`/`DB_PASSWORD` and optional `DB_NAME`/`DB_PORT` from `.env`; keep `DB_URL` in sync.
- `.env` is personal and secret: never read, print, edit, or commit it. To check it, compare against the container config without printing values. New keys go to `.env.example` with placeholders only.
- Verify a PostgreSQL connection by running `./gradlew bootRun` and checking the log for `HikariPool-1 - Added connection org.postgresql.jdbc.PgConnection` (`jdbc:h2` = fell back to H2), plus `pg_stat_activity` on the DB side. Stop the app afterwards.
- Port 8080 may be taken by another local service (e.g. nginx); use `SERVER_PORT` instead of changing code.
- `POSTGRES_PASSWORD` on the container only applies when its data volume is first initialized; if the volume is recreated, update `DB_PASSWORD` in `.env` to match.

## Team Decisions (approved 2026-11-17, override the design doc where they differ)
- D1 PKs: `BIGINT GENERATED BY DEFAULT AS IDENTITY` (ERD shows INT; not UUID). Entities extend `common/entity/BaseEntity` (id) or `AuditableEntity` (id + created_at/updated_at).
- D2 Tables: the 12 ERD tables (see Database). `rest_blocks` may be cut from MVP.
- D3 Password reset (BR-14): extra table `password_reset_tokens` (approved addition); MVP logs the reset link instead of sending email.
- D4 Base path `/api/v1` (design doc writes `/api/...`).
- D5 Error codes from the design doc (see REST API).
- D6 The design doc contains BR-01..BR-15 and HC-01..HC-09 (no BR-16..BR-32).
- D7 AI provider: Google Gemini, as in the design doc (timeout 5 s, BR-12).
- D8 No system-wide roles (actors: Guest, User). LEADER/MEMBER are per group, checked in services by `groupId`. The creator starts as LEADER; `team_groups.created_by_user_id` is historical data and grants no extra authority. Any ACTIVE LEADER of the same group may demote or remove another LEADER, including the creator; at least one ACTIVE LEADER must remain (409 `DATA_CONFLICT` on the last leader's self-demotion or self-removal). (TV1, 2026-11-27)
- D9 Audit columns only where the ERD has them; no `created_by`/`updated_by`.
- D10 Tests: H2 `create-drop`, Flyway disabled. Migrations are PostgreSQL-only and are verified by Testcontainers `@Tag("pg")` tests (`./gradlew pgTest`, approved as G3, added by F-03).
- D11 No refresh token in MVP (access JWT only).
- D12 (backend) Query windows of `GET /v1/calendar`, `GET /v1/groups/{id}/availability` and `POST /v1/schedules/generate` are valid only when `start < end` and `end - start <= 366 days` (`DateUtils.MAX_QUERY_RANGE`, full Instant precision); otherwise 400 `INVALID_TIME_RANGE`. Edit-session ranges are not capped. (TV1, 2026-11-28)
- D13 (backend) Personal task endpoints (`/v1/tasks`) cover personal tasks only (`group_id IS NULL`), including group tasks whose `owner_user_id` is the caller; a group task id there is 404. (TV1, 2026-11-28)

## Architecture
Modular Monolith + Layered: Controller -> Service -> Repository -> PostgreSQL.
- Controller: HTTP, validation, responses. No complex business logic.
- Service: business logic. Repository: data access. DTOs for request/response. Entity = persistence model.
- Never return JPA entities from the API.
- Scheduling Engine: deterministic algorithm, not LLM-dependent.
- AI Service: provider calls + output validation, behind an interface/adapter.
- No microservices, no extra frameworks. Do not rename Java packages, replace the build tool, change the API contract, or delete/rewrite modules.
- If the architecture seems wrong: explain cause, impact, options; wait for approval.

## Database
12 tables (ERD): `users`, `tasks`, `availability_rules`, `fixed_events`, `schedule_proposals`, `schedule_sessions`, `rest_blocks`, `team_groups`, `group_members`, `task_assignments`, `notifications`, `ai_request_logs`; plus `password_reset_tokens` (D3).
- Created so far: `users` (V1). Check `src/main/resources/db/migration` for the current state.
- Match ERD + data dictionary exactly before writing entities/migrations. No adding/dropping/renaming tables or columns without approval.
- snake_case, explicit PK/FK, unique + check constraints. Versioned Flyway migrations; never edit applied migrations; no destructive migrations without approval.

## Business Rules (full list: BR-01..BR-15 + Hard Constraints HC-01..HC-09 in the design doc)
**Tasks**
- Priority: LOW, MEDIUM, HIGH, URGENT. Status: TODO, IN_PROGRESS, COMPLETED, CANCELLED.
- Valid title; estimated duration = positive integer within limit.
- `is_overdue` computed from deadline + status, never stored. Soft delete per design.
- Never schedule COMPLETED/CANCELLED tasks.

**Scheduling**
- Only within valid availability; no overlap with fixed events or CONFIRMED sessions; never past deadline.
- Order: priority desc, then deadline asc (ties: remaining duration, created time, taskId). MVP: at most one continuous session per task per batch (BR-08); no splitting.
- Intervals are half-open `[startAt, endAt)`: adjacent sessions do not overlap.
- Not enough time -> return conflict info, never a wrong schedule.
- Generate creates only PROPOSED sessions, grouped in `schedule_proposals` (one active PROPOSED batch per user, with `version`). CONFIRMED/COMPLETED are protected (never overwritten/moved).
- User confirms explicitly; re-check all HC in one transaction at confirm time, check `version` (409 `STALE_VERSION`), roll back the whole batch on any conflict (BR-10, BR-11).

**Group & Assignment**
- Group creator = LEADER (manages group, assigns tasks). MEMBER can ACCEPT/DECLINE; DECLINE requires a reason.
- Assignment status: PENDING, ACCEPTED, DECLINED, REVOKED — independent from Task status.
- One source record per task in `tasks`; never clone group tasks into personal tasks. Link via `task_assignments`.
- Only ACCEPTED assignments enter a member's to-do list. Enforce authorization in backend.

**Privacy**
- LEADER sees only shareable BUSY/FREE intervals. Never expose personal task titles, private fixed-event content, personal notes, or unauthorized session details via DTO/API.

**AI**
- Provider: Google Gemini (D7), behind an `AiClient` adapter. Don't add API keys, pick a model or call the real API without approval. Send only the minimum task text (no credentials, other users' calendars or account ids).
- Flow: AI suggests -> backend validates -> user confirms.
- Uses: parse natural language into a structured task; suggest fixes for overload.
- AI never writes official tasks, changes confirmed schedules, or touches the DB.
- Validate JSON, types, deadline, priority, duration. On 5 s timeout / invalid JSON / quota: return 503 `AI_UNAVAILABLE`, user continues with manual input.

## Coding Conventions
- PascalCase types, camelCase methods/vars, UPPER_SNAKE_CASE constants, lowercase packages.
- Constructor injection. DTOs + Bean Validation. Centralized exception handling.
- No duplicated code, no needless abstraction, no hardcoded secrets.

## REST API
- JSON, correct HTTP methods/status codes, base path `/api/v1` (context path `/api` + `@RequestMapping("/v1/...")`).
- Endpoint list: design doc table "Tổng quan REST API" (paths there are relative to `/api`; add `/v1`).
- Error codes (`ErrorCode`): `INVALID_INPUT` 400, `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `RESOURCE_NOT_FOUND` 404, `STALE_VERSION` 409, `CONSTRAINT_VIOLATION` 409 (+ `conflicts[]`), `AI_UNAVAILABLE` 503. Add module-specific codes with the module that throws them.
- Consistent success/error format, meaningful error codes, no stack traces to clients.
- OpenAPI/Swagger where suitable.
- Check the existing API contract before standardizing; don't impose a new response format without team approval.
- Verify authentication + authorization on sensitive endpoints.

## Testing
- JUnit 5, Spring Boot Test, Mockito (from spring-boot-starter-test), Testcontainers PostgreSQL (`spring-boot-testcontainers`, `testcontainers-postgresql` 2.x, versions from the Boot BOM). Ask before adding other test libraries.
- Every `@SpringBootTest` (and other Spring context tests) MUST use `@ActiveProfiles("test")`. The `test` profile (`src/test/resources/application-test.properties`) forces an isolated H2 DB (`jdbc:h2:mem:planwise_test`, `create-drop`), so tests never touch the developer's PostgreSQL even when `.env` exists. Never point tests at the dev DB.
- PostgreSQL-only behavior (partial unique indexes, CHECK constraints, Flyway migrations, `ddl-auto=validate`): extend `support/PostgresContainerTest` (already `@Tag("pg")`, `@ActiveProfiles("test")`, throwaway `postgres:16` via `@ServiceConnection`, Flyway on, `validate`). Keep subclasses' configuration identical so the context is reused. Run with `./gradlew pgTest` (needs Docker); `./gradlew test`/`build` skip them.
- Test-only entities (e.g. `SampleAuditable`) also need a test-only table for `pgTest`: add `src/test/resources/db/test-migration/V9xxx__*.sql` (versions ≥ 9000 are reserved for test-only migrations). Never put test tables in `src/main/resources/db/migration`.
- Run `./gradlew clean build` if tests fail with stale-class errors (e.g. "Unable to find a @SpringBootConfiguration").
- Cover: valid/invalid input, edge cases, invalid states, missing permission, not found, DB constraints, conflicts/concurrency, API responses, cross-module behavior.
- Scheduling: overlap, deadline, availability, confirmed sessions, overload, concurrency.
- Assignment: accept, decline, revoke, permissions.
- No fake tests; don't mock away the business logic under test.
